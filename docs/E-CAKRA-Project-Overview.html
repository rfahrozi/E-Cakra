E-CAKRA

Electronic Command & Access for Court Room Administration

Pendahuluan Arsitektur & Teknologi Peran Pengguna Fitur Utama Alur Operasional Keamanan & Audit

📌 Pendahuluan

E-CAKRA adalah portal internal berbasis web yang dirancang khusus untuk Pengadilan Tinggi guna mengotomatisasi, menstandarkan, dan mengamankan pengelolaan persidangan elektronik melalui integrasi langsung dengan Zoom API.

Sistem ini lahir untuk menyelesaikan masalah operasional klasik persidangan online:

  • Pembuatan meeting manual yang memakan waktu dan rawan kesalahan (*human error*).
  • Konfigurasi keamanan ruang sidang yang tidak konsisten (seringkali lupa mengaktifkan Waiting Room).
  • Kesulitan dalam memvalidasi identitas peserta sebelum sidang dimulai.
  • Tidak adanya rekam jejak (*audit trail*) hukum yang terpusat atas aktivitas operator.
Status Saat Ini: E-CAKRA telah mencapai status implementasi MVP ~97% dengan 5 alur inti yang berjalan end-to-end secara production-ready.

🏗️ Arsitektur & Teknologi

E-CAKRA dibangun menggunakan arsitektur Containerized Modular Monolith yang stabil, berkinerja tinggi, dan mudah dikelola melalui Docker. Sistem dibagi menjadi 4 container utama yang berjalan secara terisolasi.

Backend (API Core)

Menangani seluruh logika bisnis, otorisasi, integrasi Zoom Server-to-Server, dan webhook event.

Python 3.12 FastAPI SQLModel (ORM)

Frontend (UI/UX)

Single Page Application (SPA) yang responsif, menampilkan dashboard operasional real-time.

React 18 TypeScript Vite Tailwind CSS Zustand

Database (Storage)

Penyimpanan persisten sebagai Single Source of Truth untuk seluruh entitas sistem.

PostgreSQL 16

Reverse Proxy (Gateway)

Gerbang masuk internet yang menangani SSL/TLS, *routing*, dan *rate-limiting* perlindungan serangan.

Nginx Alpine Let's Encrypt SSL

👥 Peran Pengguna (RBAC)

Sistem E-CAKRA menerapkan Role-Based Access Control (RBAC) ketat yang membagi pengguna ke dalam 3 peran (role) dengan hak akses spesifik:

Peran Tanggung Jawab & Hak Akses
Administrator Super user IT. Memiliki hak penuh atas seluruh sistem. Dapat mengelola data Pengguna, mengubah Pengaturan Sistem, mengelola sidang, dan melihat Audit Log keseluruhan.
Panitera Petugas persidangan. Berhak membuat, mengubah, dan menghapus jadwal sidang. Dapat membuka ruang sidang dan mengontrol peserta di Waiting Room.
Operator Sidang Staf operasional. Hanya berhak mengontrol peserta di Waiting Room (Admit/Hold/Reject) saat sidang berlangsung. Tidak diizinkan membuat atau menghapus jadwal sidang.

⭐ Fitur Utama (Core Features)

1. Automasi Zoom Meeting

Setiap pembuatan jadwal sidang akan otomatis memicu pembuatan Zoom Meeting di belakang layar. Konfigurasi keamanan (Waiting Room, Mute on Entry) dikunci "ON" tanpa bisa diubah oleh pengguna.

2. Live Streaming RTMP YouTube

Sistem mendukung prinsip Public Trial. Untuk perkara berstatus "Terbuka", sistem otomatis mengatur Custom Live Streaming Zoom ke kanal YouTube resmi Pengadilan Tinggi, sehingga publik tidak perlu masuk ke ruang Zoom utama.

3. Visual Triage (Validasi Peserta)

Aplikasi otomatis menganalisis nama peserta yang masuk ke Waiting Room dan memberikan indikator warna: Hijau (format baku: JPU, HAKIM, dll), Kuning (perlu review manual), Merah (nama invalid/perangkat).

4. Waiting Room Management

Antarmuka real-time (auto-refresh 15 detik) untuk mengeksekusi tindakan pada peserta (Admit, Hold, Reject). Aksi di antarmuka ini akan langsung tersinkronisasi ke Zoom Cloud via API.

5. Template Teks Distribusi

Generasi teks baku otomatis untuk dibagikan via WhatsApp (E-Berpadu/SIPP). Memuat detail perkara, link bergabung, password, dan instruksi wajib format nama.

6. Portal Publik

Halaman tanpa login (Landing Page) yang ditujukan untuk masyarakat. Hanya menampilkan jadwal sidang yang berstatus "Terbuka" beserta link siaran langsung YouTube.

1. Persiapan Jadwal (Oleh: Panitera/Admin)

Panitera login ke sistem dan menekan menu Buat Sidang. Mengisi nomor perkara, tanggal, jam, jenis sidang, dan status transparansi (Terbuka/Tertutup).

Sistem secara otomatis: Menyimpan ke database, menembak API Zoom untuk membuat meeting dengan keamanan ketat, dan mengatur sinkronisasi RTMP YouTube (jika sidang Terbuka).

2. Distribusi Undangan (Oleh: Panitera)

Panitera membuka halaman Detail Sidang, menyalin Template Distribusi dengan satu kali klik, lalu membagikannya ke WhatsApp/Email Pihak Berperkara (JPU, Penasihat Hukum, Rutan).

3. Pembukaan Sidang (Oleh: Panitera)

Pada hari H, Panitera menekan tombol Buka di Zoom pada detail sidang. Sistem akan meluncurkan aplikasi Zoom lokal milik Panitera sebagai Host utama.

4. Validasi Peserta (Oleh: Operator/Panitera)

Peserta eksternal mulai mengeklik link dan tertahan di Waiting Room Zoom. Webhook Zoom memberi sinyal ke backend E-CAKRA.

Operator membuka menu Mode Waiting Room Penuh di E-CAKRA. Sistem akan menampilkan daftar peserta lengkap dengan lencana (badge) validasi Visual Triage otomatis.

5. Eksekusi Masuk Ruangan (Oleh: Operator)

Berdasarkan indikator visual, Operator menekan tombol Admit (Izinkan) untuk JPU/Hakim, atau Reject (Tolak) untuk nama-nama acak/anonim.

Sistem mengirim perintah kembali ke Zoom API untuk mengeksekusi status peserta tersebut secara real-time di awan.

🛡️ Keamanan & Rekam Jejak (Audit)

Mengingat E-CAKRA digunakan dalam konteks peradilan hukum, aspek keamanan dan integritas data menjadi prioritas utama (Hardened Security).

  • Otentikasi Kuat & Token Blacklist: Sesi menggunakan JWT berumur pendek (60 menit). Saat user melakukan Logout, token seketika dimasukkan ke dalam basis data Revoked Tokens sehingga tidak bisa digunakan lagi walaupun durasinya belum habis.
  • HTTPS / TLS 1.3 Strict: Nginx diatur untuk memaksa lalu lintas di enkripsi tingkat tinggi dengan injeksi Strict-Transport-Security (HSTS) dan pengamanan XSS/Frame-Options.
  • API Rate Limiting: Sistem memblokir upaya Brute-force login dan serangan DDoS dengan membatasi maksimal 10 permintaan per detik per IP.
  • Verifikasi Webhook (Anti-Replay): Semua notifikasi kedatangan peserta dari Zoom divalidasi keasliannya menggunakan tanda tangan kriptografi HMAC-SHA256. Jika timestamp kedaluwarsa (> 5 menit), data otomatis ditolak untuk mencegah Replay Attack.
  • Legal Audit Trail (Immutable): Seluruh tindakan esensial—mulai dari siapa yang login, siapa yang membuat sidang, hingga operator mana yang mengklik 'Admit' pada peserta—tercatat abadi dengan timestamp UTC di tabel `audit_logs` untuk dipertanggungjawabkan secara hukum.
